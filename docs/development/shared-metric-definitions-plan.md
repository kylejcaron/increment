**Goal:** edit one definition; use it for a Terrine feature, a supported Increment experiment metric and a Malloy report without hand-translating the business logic. **Spec:** [Shared metric definitions](shared-metric-definitions-design.md), approved at `e543e9c5dc`. **Architecture:** an independently buildable wheel within the Increment repository, with no dependency on either product, plus native adapters. Co-location simplifies the first release; the wheel has its own version, not Increment's. Python ≥3.12, PyYAML, Pydantic 2, existing Ibis builders; Malloy JS + DuckDB in conformance only. No new hosted project or registry publication required for development.

## Task 1 — One definition contract and one reference dataset

**Files (Increment repo):** create `core/pyproject.toml`, `core/src/increment_metrics/{__init__,models,loader,formula}.py`, `core/tests/test_definitions.py`, `core/examples/shop/{metrics.yaml,data.sql,expected.json}`, `core/README.md`. Own the schema and fixture here only; include the fixture in conformance distribution artifacts without installing product runtimes. Build standalone wheel and sdist; expose JSON Schema for v1 from the same typed model.

- [ ] Red: `test_population_and_order_grain_are_distinct` loads the spec fixture: customers A/B/C, three order keys, no order for C. `test_formula_dependencies_and_precedence` resolves `2 * (revenue - refunds)` against named measures, including a named formula referencing another. Unknown references, duplicate definitions/YAML keys, cycles, unsupported operators/functions and a numeric non-finite literal fail at load with their source location. No dynamic language evaluation.
- [ ] Implement `load(path: str | Path) -> Catalog`, `Catalog.select(names: Sequence[str]) -> Catalog` (dependency closure, including populations and dimensions), and immutable arithmetic nodes. The closure must not require an unrelated target capability. Whole-file syntax and reference errors still fail. Top-level `version: 1`; optional named `populations` bind a unique entity key to a physical roster source; metrics choose exactly one of `formula`, `per_unit_mean: {measure, population}` or `conversion: {event_count, population}`. Ordinary formulas have no implicit eligible population. A native binding cannot silently substitute a different roster.
- [ ] Encode table/column names as identifiers, not SQL. Define row ids, entity foreign keys, event time, typed event-local dimensions and named many-to-one joins to a unique dimension key. Sums and qualifying-row counts use named filters (conjunction of typed comparisons or membership; null comparison is not implicit equality). Conditions apply to their named operand only. Distinguish source completeness from empty observed inputs; accept known-complete scope in the portable analytical fixture. Document data requirements (non-null unique keys, non-null included amounts, complete rows) and target refusal where they cannot be established. No general SQL-expression parser or arbitrary joins.
- [ ] Ship hand-derived fixture answers: A/B/C revenue & count `(60,2)/(60,1)/(0,0)`; refund sums `5/10/0`; net revenue `55/50/0`; total AOV `40`; per-eligible-user revenue `40` vs per-buyer `60`; purchase conversion `2/3` vs `1` among buyers. Add a second filter scoped only to one component, a failing duplicated dimension key, and a separate incomplete-coverage case. Place the exact input SQL, scopes and expectations together. Verify module and isolated wheel import without Ibis, Increment, Terrine or Node.

- [ ] Red: `export_malloy(catalog, *, metrics, connection='duckdb') -> str` produces a source a handwritten report can import, group and query. Execute on the golden DuckDB input with Node 22 and exact `@malloydata/malloy`/`@malloydata/db-duckdb` `0.0.438` dependencies in `package-lock.json`. Assert returned values and keys, not generated source snapshots.
- [ ] Emit native named fields for leaves and formulas in dependency order. Quote/validate identifiers and render typed literals centrally; preserve precedence and use `nullif(divisor, 0)` for `/`. Grouping overrides for business dimensions must be defined on every operand. Separate roster-backed vs fact-backed groupings; count matched non-null event keys on outer joins. For conversion, compute per-unit presence before taking eligible-unit mean; do not divide event count by eligible-unit count. Keep the generated file importable from native handwritten views. Reject selections or native bindings that cannot be represented; never overwrite a hand-authored model or return partial success.
- [ ] `export_malloy` is an offline compiler, not a physical validator. It rejects structurally unsafe joins. Non-null unique physical row/dimension/roster keys are **preconditions** for using generated Malloy; `primary_key` is not enforcement. For certified execution, the dataset owner must enforce these keys or verify them for that same immutable snapshot. `core/conformance/malloy/run.mjs` is the owner in our fixture: before running a report against its read-only DuckDB file, reject any null key or duplicate in the selected join closure, identifying relation and key. A duplicate in the dimension fixture must prevent query execution and return no metrics; a clean fixture must return the declared totals. A successful export against declarations alone makes no data-integrity claim.
- [ ] Execute the positive fixture, operand-local filter, C-only null and unknown/mis-scoped dimension cases. Keep Node and DuckDB out of the runtime Python wheel. Verify `npm ci --prefix packages/metric-definitions/conformance/malloy` then the focused Python test invoking the pinned JS runner.
