# User-authored comparisons on randomized experiment readouts

Design proposal, not a released API or implementation authorization. Baseline: `fad84bc1`. Decision requested: is a custom comparison in the same readout materially better than handing the analyst a prepared table? If not, do not add a plug-in API.

## Scope ledger and decision

| Origin | Design scope | Disposition |
|---|---|---|
| Owner: “custom estimators for users to be able to create and run in a similar pattern” | Write a Python method outside Increment; run it on the same experiment as a built-in. | Core workflow. Not a request to add a catalog of estimators. |
| Owner: “support as of and daily views optionally” and “what about a mann whitney test” | Estimators and test-only methods; the same implementation on an eligible whole, daily or as-of slice. | Core workflow. Dates select outcomes; they do not change stopping guarantees. |
| Owner: “over a base class child class pattern?” and “decide the right scope and how it interacts with everything else” | Evaluate the author interface, statistical boundaries, ingress, storage and presentation. | Design discretion, not approval of every proposal in the discussion. |
| Design decision under delegated scope | Trusted Python in process; labelled unit data; one example base class and one method to override; no authority over decisions. | Compare this candidate against prepared rows in a private dataframe spike. No stable public API or implementation approved. |
| Agent-proposed whole-window and temporal breakout comparisons | Segment support is a separate acquisition/eligibility problem. | Excluded, including when a source already declares a breakout. |
| Agent-proposed warehouse and artifact delivery | Getting warehouse data to Python introduces scan, memory and privacy costs not demonstrated by a frame probe. | Excluded: no warehouse/artifact implementation or release gate. Classify these paths honestly. |
| Agent-proposed portable code, dashboard, planning and stopping hooks | Would turn reporting code into a registered inference procedure. | Excluded, not backlog commitments. |

**Decision: test the prepared slice before committing to the plug-in.** The product candidate is a reporting-only companion to `run`: the analyst's method and the standard result share the same eligible units, cutoff and capture. They can answer different questions; “sensitivity” is inappropriate if one estimates mean lift and the other tests equality of distributions. First compare two private dataframe sketches on the same slices: a function called by the analyst versus the integrated call below. Do not ship both. If the integrated version does not remove a demonstrated source of error or repeated alignment work, stop at prepared rows; if ordinary dataframe code suffices, ship neither.

## User path and statistical contract

Proposed spelling (`UnitComparison` and result types in `increment.estimators`, not the package root):

<!-- skip: next "illustrates a proposed API that is not implemented" -->

```python
class OrdersRank(UnitComparison):
    name = "orders_rank"
    grains = {"total", "daily", "asof"}

    def evaluate(self, units, *, control, treatments):
        y, arm = units["y"], units["group_id"]
        c = y.filter(arrow.compute.equal(arm, control)).to_numpy()
        out = {}
        for group in treatments:
            t = y.filter(arrow.compute.equal(arm, group)).to_numpy()
            u, p = scipy.stats.mannwhitneyu(t, c, alternative="two-sided", method="asymptotic")
            out[group] = ComparisonValue(
                effect=Effect("probability_of_superiority", "probability", u / (len(t) * len(c))),
                test=Test("equal_distributions", "two-sided", "U", u, p, reference="tie-corrected asymptotic"),
            )
        return out

exp = exp.with_views(View.daily(), View.asof())
result = increment.run(exp, reader, comparisons={"orders": [OrdersRank()]})
result.comparisons.to_frame()  # separate from the built-in decision table
```

Example shorthand assumes `pyarrow as arrow` with the compute module imported and SciPy in the author's environment. This illustrates an asymptotic test, not a package-endorsed small-sample or all-ties procedure. With treatment first, normalized U estimates `P(T>C) + ½P(T=C)` for independently drawn units. The ordinary U test's null is equal distributions, **not** necessarily a zero mean difference, equal medians, or even the composite null that win probability equals ½. Raw U is sample-size dependent. Do not chart it as relative lift. In a fixture with treatment `[0,1,2]`, control `[0,0,2]`, the effect is `5.5/9`; duplicating every observation leaves the effect unchanged but scales U. Test-only and estimate-only output are both legal.

`UnitComparison` has one abstract computation: `evaluate(pa.Table, *, control: str, treatments: tuple[str, ...]) -> Mapping[str, ComparisonValue | Unavailable]`. Required instance name is unique within metric/run and is **only a label**. The explicit instance selects the executable. Optional tuple of pre-exposure covariate names (default empty); explicitly supported grains (default total). No methods for fetching, splitting arms, persistence, power, rendering or stopping. No required global registration, dynamic import from data, or mutable class-wide config. Already-trusted local Python, not a sandbox. Authors keep fitted state local to a slice; outcome-trained models cannot be shared with earlier cutoffs. Call exactly once per method/metric/view cell across **all arms**, not once per treatment: fits can share a control or train pooled cross-fitted nuisance models. The ordered treatment roster names estimable arms; the planner itself emits a coded unavailable row for a missing arm or missing control, never deletes the cell or calls SciPy with an empty sample. A declared treatment roster is authoritative; if absent use the existing run arm inventory, not labels discovered afresh at each date. Empty entire roster: same availability behavior as the built-in view. Contributors provide a second, independently written adjusted-mean example; no package implementation or accuracy guarantee for arbitrary learners.

Each `ComparisonValue` contains an effect, a nominal test, or both. Effect = named target, scale/units, finite point, optional ordered bounds with level and interval interpretation. Test = named null, alternative, statistic name/value, finite p in `[0,1]` and reference. No invented bounds, p-value or prior; absence is null, not zero. A method can return `Unavailable(code, reason)` for a data-dependent failure such as an unidentifiable regression. Nonempty labels, finite values and exact treatment-key coverage checked before returning a result; do not validate correctness of a user's statistical assertions by introspection. Unexpected exceptions abort the requested run with metric, view and method context and chained cause, not a silently absent companion. Results are nominal/user-supplied, never a certified estimate merely because the plug-in was present.

## Routing, evidence and identity

1. **One public entry.** `_run.run` accepts an optional metric-name → ordered method sequence. Resolve only against metrics in the selected experiment/readout. Unknown or unselected metric, duplicate method name for one metric, empty request for a named metric, or a named metric with no comparison view: pre-read coded refusal. Built-ins and `decision_method`/`sensitivity_methods` retain existing meaning. No extra column, registry initialization, data read or wire field for calls without comparisons. The observed baseline: a probe registered via `EstimatorRef('randomized.rank_probe', …)` and `register_implementation` then selected via `Method(name='rank_probe')` ran `randomized.unadjusted` and invoked the callback zero times. Do not change existing free-form labels retroactively; **never route the new binding via those labels**. Reuse declarations and evidence checks rather than adding a second process registry.
2. **One plan and capture.** `_execute.execute_views` plans all selected views before any data reads. Add the custom evidence requirements there and borrow the same verified reader, execution context, population and snapshot as the built-in reductions. No reaching into `reader._source` in user code. Respect close/offline/identity and coherence checks. Require captured coherence for an integrated comparison; a source unable to guarantee a matched snapshot must refuse, not present two live reads as matched. `View.daily/asof(values=True)` remain per-arm descriptors: never run a contrast on them. For selected comparison-producing views that include the named metric, refuse an unsupported requested combination rather than silently skip it. Select a supported subset with `views=`. No mutation of the portable `Experiment`; runtime bindings exist for this call only.
3. **Minimal input.** One Arrow table per cell: canonical `unit_id`, `group_id`, numeric `y`, and only requested pre-exposure covariates. Source owners enforce eligibility, time, missingness and data identity. Constancy does not prove temporality: callers attest the covariates were measured before exposure. Use the existing `unit_frame_covariate_columns` mapping for the projected request (expose that mapping to authors). Never pass a wide frame, connection or provider handle. Do not share an outcome-trained model with earlier cutoffs.
4. **Prepare before arm aggregation.** Reuse `UnitRowsRequest` for whole-window unwindowed mean outcomes. It has no grain; `MomentsRequest(grain='asof')` cannot provide ranks. The dataframe spike takes the calendar and per-unit preparation from frame reducers (`_frame_panel._day_population`, the eligible roster and the day-axis prefix reduction), before reduction to arm moments. Produce `(view, date, units)` one cell at a time. Match the full executable calendar curves, timezone and observation cutoff. No segmented, arbitrary-date or warehouse operation; no required `EvidenceProvider` member. If promoted, advertise dated rows via an optional capability absent in legacy declarations; never infer it from `grains` alone.

   **Capture contract.** A comparison-only baseline is *not* a built-in `Method` or a CUPED config. Add a default-empty, per-metric tuple of baseline dependencies to runtime `EvidenceScope`; include it in `EVIDENCE_REQUEST_DEPENDENCIES`. `capture_requirements` unions `(metric, declared baseline)` pairs canonically across selected views and methods. Resolve these names to the required physical streams before entering the owned snapshot and validate the identical dependency set against a borrowed context before any read. An owned context for a single view with comparisons must not take `_execute.execute_views`'s single-view shortcut around shared acquisition. Project the pinned data, never ask the live source again. The frame slice can satisfy these columns from its pinned input; an external property is refused on this path. Any later adapter for such a property must include its stream in `scope_stream_inventory`, pin the mapping, and reject a missing or changed stream instead of acquiring it late. No new wire field for calls that don't use this feature.
5. **One live comparison table.** Key its rows by metric, method label, declared view hash, optional day, population and ordered control/treatment; record capture identity, arm counts, result or unavailable reason. Order by selected view, metric declaration, date, caller's method order, then arm roster. `result.comparisons.to_frame()` exports scalar output without code. `render(result)` shows it separately as *Custom comparisons — nominal, not decision evidence*. `cells`, `effects`, `readout(view)`, `decisions` and their underlying family keys stay built-in only; the built-in projection must be explicitly labelled in documentation and in live rendering. `RunResult.to_frame()` still means all built-in cells; it never merges incompatible estimands. Refuse `results_store`, `decision_log`, whole-result pickling and `result.envelope` for mixed runs rather than silently losing custom results. Export either table intentionally for notebook use. A saved experiment keeps only its original declarations; never load executable code from saved input. No custom row enters dashboards, historical runs or `AnalysisEnvelope`.

## Interaction budget: promised versus refused

These are target capabilities, not claims about what `main` already does. Admitted core: two or more parallel arms, independent unit assignment, assigned population, one untransformed scalar mean metric (a numeric per-unit value, not necessarily positive), fixed horizon. No inference on correlated observations by accident. Explicit refusal includes the offending metric, view, method and remedy. Reuse the existing `RefusalSpec`/`CodedError` for the same hazard across ingresses; introduce one shared code only for genuinely new request or invalid-output hazards. Static issues before acquisition; missing arms/degenerate outcomes at evaluation.

| Surface | Decision and reason |
|---|---|
| `from_frame(shape='summary')` | Whole-window only in the dataframe candidate. Daily/as-of source-limited: outcomes already collapsed, no history. |
| `from_frame(shape='panel')` | Candidate: whole window and, with exposure dates, unsegmented `View.daily()` and `View.asof()`. One eligible unit per row per cell. Daily uses that day's contribution; as-of accumulates in-scope contributions per unit. Follow the existing metric/source rules for no-event zeros versus skipped values. Do not equate final as-of with whole window when rosters differ. |
| `from_definitions`, `from_unit_day_artifact` | No target in this release candidate, including whole window. Refuse before executing a warehouse query or loading an artifact. Integration is unfinished where the source could supply rows; missing underlying detail is source-limited. Existing built-ins continue working. Revisit only for a named warehouse use case and a measured bounded one-scan projection. |
| `from_moments` | Unit-only callback is source-limited. Distinct arm distributions can have identical count/mean/variance but different ranks. No fallback, no second aggregate-method API; built-in moment methods unchanged. |
| `from_switchback_frame`, cluster, observational, encouragement, logged policy | Not supported by the independent two-sample construction. Designs target schedules, clusters, identified adjustments, uptake or policy values rather than independent unit arms. The observational registry and estimates, specialist CATE/targeting and other families remain unchanged. No calling a companion on these designs by dropping IDs. |
| CUPED, prior, multiplicity roles | Existing built-in method can still be CUPED-adjusted, shrunk, primary, secondary, sensitivity or guardrail. The companion receives **unadjusted** declared outcomes, owns any adjustment it reports and never inherits the built-in's posterior, role, significance, alpha allocation or guarantee. Cross-fitting is allowed inside a slice on declared baseline columns. Never use a companion's null to satisfy a different planned hypothesis. |
| Conversion, retention, ratio, quantile, winsorization | Out of this construction's initial declared scalar-mean scope. Do not pass a numerator for a ratio, daily indicators for an immature retention band, or raw values for a winsorized metric. These are mostly unimplemented combinations, not universally unsound. A user can declare an appropriate separate scalar outcome; this is not equivalent to the refused target. |
| Time, segments, missingness | Grains opt-in per method. Exclude all breakouts, segmented or cohort-indexed curves, selected-date selectors, windowed/maturity-filtered and triggered comparisons. Refuse rather than substitute a pooled or full-calendar comparison for an unsupported user request. |
| Sequential, stopping, power, margins, planning, dashboard | Fixed-look series are pointwise, not a sequential procedure or jointly valid bands across looks/segments. Refuse sequential plans/captures for mixed runs. No power/MDE inference, releveling, margin comparison, BH/FCR or saved decision from a custom p-value; no implicit dashboard plot on a lift axis. These require distinct statistical/result contracts, not boolean declarations on the comparison class. Existing built-ins keep those capabilities. |

## Can this earn its place?

Baseline alternative **A**: use SciPy/NumPy directly on the caller's own dataframe. For one clean summary snapshot, A wins; don't build a framework to save a single SciPy call. Alternative **B**: expose a prepared unit slice and stop. B is adequate for standalone notebook work. Prefer the integrated design only if it removes the need to reconstruct the cohort, coordinate separate snapshots, and manually align method results with built-in windows and arms in a real workflow. A third alternative, shipping Mann–Whitney as a built-in, avoids a plug-in API but does nothing for an analyst's independently written adjusted estimator. Nothing here claims measured customer demand.

Give the prepared-slice alternative a fair comparison: in the private sketch `for cell in prepared_slices(exp, reader, metric="orders", views=(daily, asof))`, each cell already carries its view/date, arm labels, counts, capture identity and `cell.units`. The analyst can call ordinary SciPy or fit a model, with no joins to raw events. The integrated candidate must beat **this**, not just a naive filter. Use the same frozen panel and comparison functions in both trials. Ask the analyst to put both custom results next to built-in rows and repeat after changing the declared views. Record wrong/missing coordinates, duplicate eligibility or alignment code, whether an extra capture was needed and which interface they would actually keep. The private sketches need neither production result serialization nor warehouse changes; production integration gates apply only to a winning design.

**Concrete evidence, not a demand forecast.** In a six-unit sparse panel with staggered entry, the only physical rows on January 2 are control `3` and treatment `1`: filtering the raw frame would give win probability `0`. Increment's executable `View.daily()` counted three per arm; its arm means matched the complete daily arrays `[0,0,3]` and `[0,0,1]`, whose win probability is `4/9`. The same day's `View.asof()` means matched cumulative arrays `[5,0,3]` and `[7,0,1]`, whose win probability is `1/2`. Only **counts and means** were verified against the built-in view; individual membership and ranks were calculated independently. This favors prepared units; it does not distinguish an integrated plug-in from a prepared-slice API. The existing runner admits full calendar curves, not nonempty `day_domain` or `through_day` (`_runnability.scope_refusals`); this proposal does not change that.

References: [Increment's estimator/evidence boundary](adding-an-estimator.md), [tea-tasting's comparison base class](https://github.com/e10v/tea-tasting/blob/90306f16dbba45a68f655e5f5d35b6e6f7a811bc/src/tea_tasting/metrics/base.py#L61-L101), [SciPy's Mann–Whitney null and tie conventions](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.mannwhitneyu.html), and [Guo et al., Algorithm 1, for pooled cross-fitting](https://proceedings.neurips.cc/paper_files/paper/2021/file/488b084119a1c7a4950f00706ec7ea16-Paper.pdf). The base class is for discoverability and defaults. A function works fine on a single prepared slice; inheritance does not confer statistical guarantees.

Acceptance before promoting a stable API:

- Have an analyst implement a rank test and another implement an adjusted mean without editing Increment, mutating registries, private imports, or writing exposure/date joins. Exercise a sparse, staggered panel with tied outcomes, no-event days, skipped observations, an absent arm and a late entrant. Verify exact **unit membership and values**, U against enumerated comparisons, and adjusted point estimates against an independent reference with folds fixed by ID. No claim about the calibration of arbitrary third-party methods. Changing future outcomes must leave earlier results unchanged. The previous 160-unit local probe established only input shape and matching arm counts/means on a dense-after-entry fixture, not these properties.
- Catch pairwise dispatch with **two simultaneously estimable treatments**. Fit one common within-arm slope to `(baseline, outcome)` pairs: control `[(0,0),(2,2)]`, A `[(1,1),(3,3)]`, B `[(2,0),(4,8)]`. The pooled slope is `2`; both baseline-adjusted treatment differences are `−1`. Pairwise fits incorrectly give `0` and `−2`. For each metric/view/date verify one call with the complete declared order (include non-alphabetical `B,A`), both labelled outputs against this independent reference, and unchanged results under input permutation. Separately test a missing arm rather than weakening this all-arms case.
- Hold all built-in declarations fixed. With/without the companion, compare each built-in estimate, failure reason, decision method, hypothesis and family outcome at matched data. A tiny U-test p-value paired with a null built-in mean decision must not change a launch decision. Two parameterizations under colliding labels must refuse, not overwrite. The selected callback must run, not silently select `randomized.unadjusted`. With no unit evidence, refuse before any query/callback. Malformed custom results and legitimate unavailable cells have different outcomes.
- Match whole-window output from summary and equivalent panel units. Compare each supported panel date against an independently prepared summary at that cutoff. On the other four ingress paths verify deliberate refusals, not fabricated results. If promoted, record this evidence in the capability catalog and generated table; check prior wire payloads, default provider compatibility, eager persistence refusals and explicit live projections.
- Only the adjusted comparison requests `pre`. Check the run keeps the originally captured values and rejects a borrowed context that lacks that dependency before any callback. A test provider whose separate baseline stream changes after capture must either return the pinned baseline or refuse on identity change, never produce a mixed result; enabling an external property adapter is not part of the dataframe gate.
- Compare 1 versus 30 dates on a sparse in-memory panel: record shape, elapsed time, bytes and peak memory against preparing the same slices once. A second method with identical inputs adds no acquisition; retaining a dense units × dates intermediate for the entire run fails. No extra reads or row materialization on ordinary `run`. Rank calculation still costs time per date. This gate covers frames, not warehouse performance.
- **Go/no-go:** if no real consumer values the integrated report over B, or per-unit membership/capture parity or bounded acquisition cannot be demonstrated, do not stabilize this API. Reconsider the smaller prepared-data alternative on its own merits. If the need is actually launch decisions, reopen the design around registered hypotheses, algorithm identity and calibrated inference rather than promoting this reporting contract by fiat.

**Difficulty:** the rank callback is small. Preparing exact dated rows, pinning baseline dependencies, and keeping unlike effects out of decision and storage paths are the substantive work. The private frame comparison can be evaluated without committing to changes in the public API, wire formats, warehouse or provider protocol. Warehouse delivery or decision-eligible methods would each need a separate design and evidence of demand. This document authorizes neither.
